# Folder sharing implementation plan

Task 1 delivers the server identity check shared with session actions. Task 2 prepares the Windows drive backend. Tasks 3–5 deliver one ordinary RDP share, and task 6 tests the Windows build against the three remote hosts. Each leaf is a focused implementation or test session, estimated at one to three hours.

- [x] 1. Establish the server identity used by both features
- [x] 1.1 Verify the peer on the connection that will use it
  - Return the observed SHA-256 SPKI and normalized endpoint only after the TLS handshake verifies the server signature and validates the chain and DNS/IP name or a confirmed endpoint pin.
  - Use a credential-free discovery connection to present a candidate key. The actual session or credential test must prove the same identity on its own connection.
  - Fixtures cover valid chain, trusted key, wrong name/port, changed key and bad handshake signature. A discovery result alone conveys no permission.
  - _Boundary: TLS peer verification_
  - _Requirements: 1.4_
- [x] 1.2 Integrate server identity review into the saved-host menu
  - Show the endpoint and observed fingerprint, including old and new keys on change. Save a pin only after the operator confirms it for that endpoint.
  - Store pins atomically outside exported profiles. Bind confirmation to the selected host revision. On cancellation or write failure, retain the prior trust decision.
  - A test can review and confirm a self-signed host without a folder grant or a credential exchange. A fresh connection accepts the confirmed key and withholds trust after rotation.
  - _Boundary: Saved-host menu and TLS peer verification integration_
  - _Depends: 1.1_
  - _Requirements: 1.4_

- [x] 2. Establish the native Windows fixture and dependency lock
  - Resolve compatible IronRDP protocol/native drive crates and native folder picker on the current MSVC toolchain. Keep platform-specific dependencies Windows-scoped.
  - Create a disposable directory fixture under the configured project artifact directory. Reuse its sentinels, read-only and writable files, and sparse file with data above 4 GiB in subsequent tests.
  - The locked build can create a single redirected drive and round-trip a decoded request through the upstream completion types in the fixture.
  - _Boundary: Windows drive dependencies and fixture_
  - _Requirements: 2.1, 2.2, 3.1, 3.2_

- [x] 3. Keep a single explicit folder grant per saved host
- [x] 3.1 Persist grants and invalidate them with profile mutations
  - Bind a grant to the profile ID, endpoint, server key, volume/directory identity, share name and mode. Serialize revocation with retargeting, import and single/cascaded deletion.
  - Test restart, failed save/revoke, changing an address away and back, display-name edits, duplicates and imports. Missing or corrupt data leaves sharing off. A stale grant never reactivates.
  - _Boundary: Folder grant store and saved profile mutation integration_
  - _Depends: 1.2_
  - _Requirements: 1.1, 1.2, 1.3, 1.4_
  - 2026-11-18: `store/share_grants.rs` keeps grants in `share-grants.json`. The library revokes them inside its transactions before a retarget or (cascaded) deletion commits, and reconciles them at startup and on reload. Independent review found no blocker. Carried into 3.2: confirmation must check the host and save the grant inside the library mutation lock.
- [x] 3.2 Integrate the native folder picker and grant controls
  - Issue opaque selections for local drive-letter subdirectories and reject volume roots. Show host/port, key, folder, portable name and mode together. Start at read-only and offer explicit read/write.
  - Register read, select, confirm and revoke commands. Reject expired selections or endpoint changes at confirmation. Cancel, failed writes and repeated revoke show the committed state.
  - In the saved-host editor, saving shows “next connection.” An active grant displays how to end access immediately by disconnecting. Confirming a new host key alone leaves the folder withheld.
  - _Boundary: Host editor and folder grant command integration_
  - _Depends: 2, 3.1_
  - _Requirements: 1.1, 1.2, 1.3, 1.4_
  - 2026-11-18: `commands/folder_share.rs` adds get/select/confirm/cancel/revoke. A folder is offered only after a fresh connection proves a trusted key (chain or confirmed pin). The chosen directory must resolve to itself (no link, junction or substituted drive on the way), sit on a local NTFS/ReFS drive letter and keep its volume/file ID until confirmation, which saves under the library lock. The UI is **Share folder…** in the saved-host menu and a summary in the host editor; it states that sessions do not offer the folder yet. Independent review: no blockers; both should-fixes resolved. Left for later: a rotated server key still shows the grant as saved (effective status is 5.3), and the trust check is not repeated if the picker stays open for a long time (5.2 re-verifies the session key).

- [ ] 4. Confine Windows filesystem requests to the granted directory
- [x] 4.1 (P) Bind the selected root and retain descendant handles
  - Open the authorized volume/directory by verified identity with retained no-reparse handles. Use the approved upstream extension or ancestor-guard approach. Fail closed if confinement is unavailable.
  - Keep the target and its ancestor chain guarded until the final operation on each remote handle. Deny links, namespace escapes and multiply linked targets whose aliases cannot be confined.
  - In the local fixture, replace a root, move an ancestor or attempt to move an open target outside while a request is pending. Outside contents and metadata stay protected through the last I/O.
  - _Boundary: Windows filesystem handles_
  - _Depends: 2_
  - _Requirements: 2.1, 2.2, 2.3, 2.4_
  - 2026-11-18, part 1: `rdp/folder_share.rs` `BoundRoot` guards the root and every ancestor with read/traverse handles that deny delete sharing, so the native backend's reopen by NT path keeps reaching the granted directory. It verifies the volume/file ID under the guards and fails closed on links, replacement, missing folders and concurrent renames. Part 2: `LinkSafeBackend` wraps the native backend and refuses mutating opens of files with more than one hard link (read allowed). Measured on NTFS: a folder holding an open file cannot be moved; a file opened with delete sharing can be. Per the user's decision of 2026-11-18, such an already-open handle stays usable, while new opens always resolve from the bound root.
  - 2026-11-19, review findings fixed: stream names count the links of their file; link counting fails closed except on not-found; a rename that replaces a multiply linked file is refused; binding re-checks every guard and requires the root's final path to equal the granted path. Remote hard-link creation cannot reach the backend (ironrdp-rdpdr 0.9 does not decode FileLinkInformation). Tests decode the refusal replies' status, completion ID and file ID. The short-name binding test runs only on volumes that create short names (the Windows CI runner's C: drive). Same-user `DefineDosDevice` remapping is out of scope (design).
- [x] 4.2 Enforce read-only and ordinary workstation permissions
  - Allow list/read in read-only mode. Deny mutating open dispositions, writes, truncation, delete-on-close, rename, streams, metadata/security changes and mutating or unknown control operations.
  - In both modes, reject privilege-enabling requests before delegation. Enforce the workstation user's ACLs and surface a denied operation to its caller.
  - Tests verify bytes and metadata after every attempted mutation and confirm ordinary read, short read, EOF, zero-length and sparse high-offset cases.
  - _Boundary: Windows drive access policy_
  - _Depends: 4.1_
  - _Requirements: 2.1, 2.2, 2.3, 3.2, 3.3_
  - 2026-11-19: read-only mode is the native backend's own (`RedirectedDrive::new(.., read_only)`), and `ShareBackend` (formerly `LinkSafeBackend`) adds the privilege rule. The native backend enables SeSecurityPrivilege for SACL access and backup or restore privileges for backup-intent security, so in both modes a create with `ACCESS_SYSTEM_SECURITY` and any security query or change that touches the SACL, label, attribute, scope, trust label or backup parts gets STATUS_PRIVILEGE_NOT_HELD before delegation. Tests drive the real native backend: in read-only mode nine mutating creates (write, overwrite, supersede, delete-on-close, attributes, DACL, new stream, new file, new folder) and, through a read handle, write, truncation, rename, DACL change and object-ID creation all return MEDIA_WRITE_PROTECTED, an unknown control code returns NOT_SUPPORTED, listing works, and names, bytes, sizes, times and attributes are unchanged. Reads cover whole, short, zero-length, end-of-file (END_OF_FILE) and a 64 MiB offset that reads zeros. A read-write share writes with the user's rights and reports ACCESS_DENIED for a read-only file, leaving it unchanged. The high-offset file is not marked sparse; its unwritten range reads as zeros either way.
- [x] 4.3 Support scoped creation, copy, rename and delete
  - Guard source and destination parents across rename, allow in-folder operations, and protect the grant root from removal or rename. Deny remote hard-link creation and outside destinations.
  - Verify create/list directory, write, flush, close and rename/delete with ordinary access. Refused local operations and competing local opens return the appropriate filesystem error.
  - Fixture copies match independent hashes. Renaming into a replaced parent leaves the outside sentinel untouched.
  - _Boundary: Windows drive operations_
  - _Depends: 4.2_
  - _Requirements: 2.2, 2.3, 3.2, 3.3_
  - 2026-11-19: the native backend opens every path and rename target relative to the root handle with `OBJ_DONT_REPARSE` and rejects `..`, stream and device names, so in-folder operations need no extra guard. `ShareBackend` adds one rule: the share root is never opened with DELETE access or delete-on-close (ACCESS_DENIED); broader access that would include DELETE fails on the root guard. Remote hard-link creation cannot occur (4.1). Tests in `folder_share/tests/policy/operations.rs` bind the root before the drive opens, as a session will. They cover folder and file creation, chunked writes, flush, close, listing, rename with and without replacement, deletion by disposition and on close, and DIRECTORY_NOT_EMPTY. A 3 MiB remote copy in 256 KiB chunks matches the source's SHA-256. Rename to `..`, and rename or create through a parent replaced by a junction, fail with nothing new outside and the outside sentinel unchanged. A local exclusive open and a local open without delete sharing give SHARING_VIOLATION; deleting a read-only file gives CANNOT_DELETE.

- [ ] 5. Integrate redirection with the desktop session
- [x] 5.1 Service overlapping file requests off the interactive path
  - Dispatch ordered local I/O through a bounded per-session worker, cap handles, queued bytes, request count and reply batch size. Drain synchronous and deferred completions fairly alongside input and rendering.
  - Track generation/device/completion IDs, operation, payload length and peak outstanding count. Each live request receives one correctly shaped reply, including overload and filesystem errors.
  - Interleave reads, writes and deferred locks/notifications across file IDs. Stalling disk still lets the session process input. The fixture reports matching completions and file bytes.
  - _Boundary: RDPDR processor and session worker integration_
  - _Depends: 2, 4.3_
  - _Requirements: 2.4, 3.2, 3.3, 3.4, 3.5, 4.3_
  - 2026-11-19, part 1: `rdp/folder_share/worker.rs` `WorkerBackend` is the channel's backend. It admits each drive request against limits (64 requests, 16 MiB of write payload, replies in batches of 16) and queues it for one worker thread that owns `ShareBackend` and the bound root. Over the limits, a duplicate completion ID or a stopped worker gets an immediate reply of the operation's shape (INSUFFICIENT_RESOURCES or INVALID_PARAMETER); a backend error gets UNSUCCESSFUL. Completions and the native deferred ones (locks, notifications, polled every 20 ms) return through `poll_deferred_messages` in bounded batches with a wake callback. Each request is tracked by device and completion ID with its operation and payload length; teardown logs unanswered requests as interrupted, closes the queue without waiting, and the worker then closes its handles and releases the root guards. Tests use a scriptable fake disk; the module is platform-independent and runs on Linux CI. Part 2 (with 5.2): the session loop awaits the worker's `tokio::sync::Notify` in its `select!` alongside the PDU reader, commands and timers, and sends one bounded batch per wake through `process_svc_processor_messages`; the worker re-notifies when more replies wait.
- [x] 5.2 Attach one drive to the authorized connection and tear it down on disconnect
  - Check the effective grant, current peer and accessible root after TLS and before static channels are advertised. Disabled, stale, inaccessible or unverified grants omit the channel and device name.
  - Start a fresh worker and handle table on every reconnect. Stop admissions and cancel pending I/O on teardown. Return errors while the channel is available and record interruptions when the socket is gone.
  - Exercise disconnect mid-write, reconnect with changed grant and simultaneous sessions. Observe worker termination, handle release, rejection of late completions, and a usable desktop after a share-only failure.
  - _Boundary: Connector and session lifecycle integration_
  - _Depends: 1.1, 3.2, 5.1_
  - _Requirements: 1.1, 1.3, 1.4, 1.5, 2.4, 3.1, 3.4, 3.5_
  - 2026-11-19: the connect command hands the session a grant source that each connection attempt reads again, so a reconnect sees a revoked or changed grant. After the TLS handshake and before `connect_finalize` sends the channel list, `folder_share/attach.rs` requires the grant's address to match, verifies the server key against the reviewed one with `SignedTls::verify`, binds the folder (off the async runtime) and starts a fresh `WorkerBackend` over `ShareBackend` and the native drive, then attaches `Rdpdr::with_drives` for one drive. Any mismatch or failure logs why and connects without the channel or a device name. The channel's own start resets the backend and restores the drive. Dropping the session's stage drops the worker, which closes handles and releases the guards. Windows only; other builds log that folder sharing is unavailable. Tests use real TLS handshakes with the peer-identity fixtures: the reviewed server gets the folder and holds it in place until the channel ends; a read-only grant gives a read-only drive; another address or key, or a replaced or missing folder, gets none; two sessions share one folder independently; every attempt reads the grant again. First real-host runs, 2026-11-19: xrdp accepted the drive at once; its read opens use forward-slash paths, which the share now normalizes. Windows joined the drive channel but sent nothing on it until the client also registered the audio channel (`rdpsnd`, with no formats), as FreeRDP and IronRDP's own client do; with it Windows lists and copies. Announcing the channel as INITIALIZED made no difference. An IronRDP-based server (hypr_rdp) sent nothing on the drive channel; it may not implement drive redirection. Per-request debug logging of the drive channel ran on the session loop and made the pointer stutter during listings; it is off again. Copies stalled the session for another reason, measured on the Windows host: the server reads in 1 MiB pieces, one reply took 620-675 ms to write at about 1.5 MB/s upstream, and the loop was inside writes most of each second. Replies now go out in slices cut at TPKT boundaries, one per loop turn, and the socket's send buffer is capped while a folder is shared; both follow the per-host File transfers setting (responsive 16 KiB / 32 KiB, balanced 64 KiB / 128 KiB, fastest whole / system). The maintainer tested this on 19 November and accepts it as good enough, not perfect: the uplink stays saturated during a copy (about 1.5 MB/s, 690 ms of each second in writes with the balanced setting). A separate writer that sends input and acknowledgements ahead of file data is the known next step if it needs to be better (task 6.2).
- [x] 5.3 Show effective status from protocol evidence
  - Use the existing session details to show effective access mode and latest failure separately from the host's saved preference.
  - Show offered after the announcement is written, accepted after the matching acknowledgement, and access observed after a successful file operation reply is written. Keep explicit refusal, unsupported, inaccessible, unverified and unknown outcomes distinct.
  - Drive the UI with actual session events in a fixture. No reply and failed reads cannot advance the result to successful access. Retain the desktop layout and viewport.
  - _Boundary: Session event and existing status details integration_
  - _Depends: 3.2, 5.2_
  - _Requirements: 1.3, 1.5, 1.6_
  - 2026-11-19: `rdp/folder_share/status.rs` holds a fresh `ShareStatusCell` per connection attempt, carried by `ConnectionOutcome::RealSession` and published as `SessionInfo.folderShare`. States: off, unsupported, unverified, folderUnavailable, unknown, negotiating, offered, accepted, accessObserved, refused (with NTSTATUS), ended, plus the drive name, mode and the latest failure. Evidence: the connector records why no folder was offered; `WorkerBackend` marks offered when the channel hands it the user-logon event (the drive announcement follows in the same step; RDP 5.1 servers that take drives before logon are announced earlier, so offered may come late there), accepted or refused from the server's device-announce reply, and access observed only from a successful reply on its way out; failures are recorded beside the state, ignoring routine not-found, end-of-file and unsupported-control results. The worker reads each reply's header on its own thread. The bottom bar shows `Folder: <state>` next to Clipboard, hidden when no folder is chosen, with a menu for name, mode, explanation and last failure. Tests: state transitions and JSON in Rust; a real-TLS attach test that walks negotiating → offered → accepted, a refused write that stays accepted with a failure, a read that becomes access, and ended on teardown; frontend label tests from backend-shaped session events. The folder dialog's preview note now points to the bottom bar.

- [ ] 6. Validate ordinary transfers and measure the cost of copying
- [ ] 6.1 Verify the Windows build with ordinary tools on all three hosts
  - Run focused frontend tests and native Windows nextest plus doctests. Exercise the built app against the Windows workstation and both designated Linux hosts. Record actual server software/build, client build, known policy and offered name.
  - Record the observed UNC or mount path. Use Explorer or PowerShell on Windows and normal shell tools on Linux. Confirm RO write denial and independently hash RW copies in both directions, including an empty file and directory operations.
  - Record successful access, explicit refusal, unsupported capability or an inconclusive result per host in the spec's validation report. Preserve outstanding checks if a server is unavailable.
  - _Boundary: Windows client real-host acceptance_
  - _Depends: 4.3, 5.3_
  - _Requirements: 1.5, 1.6, 2.1, 3.1, 3.2, 3.3, 4.1, 4.2_
- [ ] 6.2 Benchmark ordinary transfers alongside interactive typing
  - For each usable host and direction, fix build, resolution, profile, network and storage conditions. Repeat a single large file and a tree of small source files with consistent cache state, plus the same typing workload without transfer.
  - Send a repeatable sequence of unique text markers to a remote editor or terminal. Capture each input timestamp and its first matching visible echo on a single client clock, using timestamped input and a synchronized screen recording. Save the paired samples with clock precision, capture rate and missed echoes. Exclude unrelated frames.
  - Record copy program, payload size, elapsed time, effective throughput, session RX/TX deltas, peak actual outstanding requests, and median/p95 input-to-visible echo. Verify hashes and the tree manifest.
  - The report includes the matched no-copy typing baseline and identifies which hosts show both room for a speed gain and independently schedulable requests.
  - _Boundary: Transfer and typing benchmark_
  - _Depends: 5.1, 6.1_
  - _Requirements: 3.4, 4.3_
- [ ] 6.3 Evaluate segmented copying only where the baseline justifies it
  - If no host shows a useful opportunity, close the evaluation with the measured reason. Ordinary sharing is ready for its own release decision after acceptance.
  - Where justified, use a test copier to compare one range with bounded disjoint parallel ranges on the same file and RDP connection under matched cache conditions. Confirm actual overlapping requests, byte-for-byte output, throughput, transferred session bytes and typing latency.
  - Record the result per host and whether an explicit copy command warrants a separate proposal.
  - _Boundary: Transfer benchmark_
  - _Depends: 6.2_
  - _Requirements: 3.4, 4.4_
